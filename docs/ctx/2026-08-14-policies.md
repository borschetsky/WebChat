## What I found — the inventory is the work

Of the nine switches on the design:

- **`members_can_create_groups` — the only one enforced.** Read by `POST /hey/creategroup`
  (`HeyController.cs`). Owners and admins are exempt regardless of the value — the policy
  restricts who may create a group, it is not a kill switch for group creation, and a
  workspace that turned it off must still have a way to make one.
- **`sessions_end_on_password_change` — already enforced, unconditionally, and therefore not
  a switch at all.** `UserService` already rotates `User.SecurityStamp` on every password
  change; every token signed with the previous stamp stops authenticating on its next
  request. Sent to the client as a locked "always on" row
  (`WorkspacePolicy.AlwaysOn` → `["sessions_end_on_password_change"]`) rather than offered
  as something that could be turned off.
- **The other seven have no enforcement point anywhere in the codebase**, confirmed by grep
  rather than taken on faith: require admin approval for invites (invitations are already
  admin/owner-only — there is no member-proposes flow to gate), allow guest accounts (no
  guest concept exists), auto-deactivate after 90 days idle (no general activity timestamp,
  no scheduler), members can delete their own messages (**message deletion does not exist in
  the app at all** — no endpoint, no service method, no client call; confirmed by grep across
  `Controllers/*.cs` and `WebChat.Services/*.cs`), retain messages indefinitely (needs a
  retention job), require 2FA (nothing), confirm sign-in from a new device (no device
  tracking). These render as inert rows tagged "Not enforced yet."

So one working switch out of nine is the honest outcome, not a shortfall — see decision 1.

## Decisions and trade-offs

1. **The server is the sole authority on what is enforced; the wire contract is the presence
   of a key.** `GET /api/admin/policies` returns only what something actually reads. The
   client renders any catalogue row missing from `policies` as inert. This is the safe
   direction: a client one deploy *ahead* of its server shows a row as inert, not a switch
   nothing honours — the reverse (client decides what's enforced) is exactly the lie the
   slice was built to remove.
2. **jsonb blob, not a column per policy.** Adding a policy becomes a product decision, not a
   migration. Cost: nothing constrains the contents at the database, so unknown keys must be
   refused at the endpoint (`unknown_policy`) and are silently dropped on read.
3. **Defaults must equal the behaviour that predates the policy**, or shipping one silently
   takes something away from every member with no release note able to reliably prevent it.
4. **Owners/admins are exempt from `members_can_create_groups` regardless of its value** —
   otherwise a workspace that turned it off would have no way to create a group at all.
5. **The policy cache is process-local, same shape as `IConnectionAborter`.** A write
   invalidates only the instance that served it; the 30-second TTL is what bounds how long a
   second instance can disagree, and it is deliberately not configurable — a knob there would
   eventually be turned up by someone chasing query counts.
6. **The audit entry stores the policy key plus both new and previous value.** The previous
   value is what answers "did this actually change anything." The client resolves the key to
   wording at render time through the same catalogue the screen uses, so relabelling doesn't
   require migrating a year of history, and an unknown key degrades to the raw key rather than
   vanishing.
7. **The singleton is enforced with a Postgres `CHECK` constraint, not just convention.** The
   entity claims "exactly one row, ever"; without the constraint that claim is only as strong
   as every caller remembering the same id, and a second row means half the process silently
   reads a configuration nobody set. Same instinct as the audit log's append-only trigger.

## Known issues / follow-ups

- **Two findings worth generalizing, not specific to this slice:**
  - A heavy MUI component imported into a lazily-loaded route lands entirely in that route's
    chunk. `vite.config.ts`'s vendor groups carry `tags: ['$initial']`, restricting each
    group to modules already in the entry's static import chain — a component reachable only
    through a lazy route (MUI `Tooltip`, and Popper with it) cannot be hoisted into
    `vendor-mui` and gets bundled into the route instead. Two `Tooltip` hints took the admin
    chunk from 33.98 kB to 67.10 kB; replaced with a native `title` attribute (as the
    Overview's chart bars already use) and it returned to 36.25 kB. Only visible in
    `npm run build` output, not `tsc` or the dev server — worth checking the build output
    before importing a new MUI component into a lazy route.
  - `inputProps` had survived here too: `AdminPolicies.jsx` used
    `inputProps={{ 'aria-label': label }}` on every `Switch`, and MUI v9 drops it silently, so
    every switch's only accessible name was being discarded. Same defect class as
    `ComposeDialog` (2026-08-07 modeless-compose-flow note) and the `AvatarGroup` slot-name
    issue (2026-08-07 group-avatar-stack note).

    **Followed up in commit `3d347de`, which is where the useful part is.** Grepping the rest
    of the client for the same spelling found three more live sites — both `Switch`es in
    `AppearanceControls` (in a `ListItem`'s `secondaryAction`, so the `ListItemText` beside
    them names nothing) and the row-select `Checkbox` in `AdminMembers`. Fourth sighting, and
    every one so far had been found by accident: these components are used from `.jsx`, where
    nothing type-checks the props, so per-component tests only ever cover the instance somebody
    already thought to look at. `src/test/mui-drift.test.tsx` now scans `src` instead, finding
    the nearest JSX opening tag before each `inputProps` and failing if it is one of
    `Checkbox`/`Switch`/`Radio`.

    Two things that pass had it been done carelessly. **The rule is narrower than "v9 dropped
    `inputProps`"** — it is gone from the `SwitchBase` family only; `InputBase` still takes it,
    and `SearchField` and `Composer` use it correctly, so a sweep for the bare prop name would
    have changed working code. A test pins that boundary. And the **first version of the scan
    passed against source that was provably broken**: a single regex spanning the tag
    (`<Checkbox[^>]*inputProps`) ends its character class at the `>` inside
    `onChange={() => …}`. Running the guard against the unfixed tree first is what caught it —
    which is the `fix-flow` step, applied to a test that guards a class rather than a defect.
- **`Admin__BootstrapOwners__0` is still absent from the DigitalOcean app spec**, confirmed
  again in this pass (15 env keys, not that one). Nothing from #70–#75 is reachable in
  production until it is set by hand in the DO console — `doctl apps update --spec` must not
  be used for this, since it replaces the entire spec and secrets read back as encrypted
  placeholders (per the 2026-08-11 workspace-roles note).
