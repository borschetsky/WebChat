## The finding that matters most

`m.Type != MessageType.System` in LINQ does **not** mean `WHERE "Type" <> 'system'` in SQL.
Messages written before the `Type` column existed have `Type` NULL and are ordinary user
messages. EF translates `!=` with null semantics — effectively
`"Type" <> 'system' OR "Type" IS NULL` (`OverviewService.cs:27-39`) — so those rows are
counted, which is right. Hand-written `WHERE "Type" <> 'system'` drops them silently,
because `NULL <> 'system'` evaluates to NULL, not true.

Found by cross-checking the live endpoint against `psql` on the production database: the
endpoint said `wrote: 7`, a hand-written query said `2`. **The endpoint was right; the
query was wrong** — 5 rows had `Type IS NULL`. The failure mode here is inverted from the
usual one: a mismatch's first instinct is to distrust the code, and in this case the code
was correct. `CLAUDE.md`'s system-message bullet now carries this as a permanent warning
(`CLAUDE.md` diff in commit `e16ecc7`); anyone auditing these numbers by hand needs
`("Type" IS NULL OR "Type" <> 'system')` or they will "find" a bug that is in their own
query.

## Decisions and trade-offs

1. **Funnel stages are cumulative subsets**: registered ⊇ confirmed ⊇ joined a conversation
   ⊇ sent a message (`OverviewService.cs:119-145`, `AdminFunnelStageViewModel`'s doc comment
   in `AdminOverviewViewModel.cs:19-25`). A stage that is not a subset produces a shape that
   looks like a funnel but cannot be reasoned about like one — enforced in code by
   `AND`-ing each stage's own condition onto the one before it, and pinned by a test
   (`The_funnel_narrows_at_every_stage`) plus a deliberately adversarial one
   (`An_unconfirmed_account_in_a_thread_does_not_widen_the_funnel`, `OverviewServiceTests.cs:219-231`).
   "Sent a message" is the last stage rather than something softer like "signed in" because
   it is the only one the app actually records — same limit `AdminMemberViewModel
   .LastActiveUtc` carries and documents (from #71's note).
2. **Percentages are of the widest stage, not of the total** (`AdminOverview.jsx:124-125`,
   `share(n)`), so the first bar is always full and each one below reads as the share that
   survived.
3. **Chart buckets are midnight-UTC days, not a rolling 24 hours**
   (`OverviewService.cs:59-63`) — a sliding bucket would make yesterday's bar change on
   every reload.
4. **The chart is gap-filled** — all 14 days, including zero days
   (`OverviewService.cs:81-94`, pinned by
   `The_chart_always_has_fourteen_days_including_empty_ones`). Without it a quiet Sunday
   disappears and the bars silently re-space, so two charts of the same fortnight look
   different.
5. **Keys cross the wire, labels do not** — funnel stages are `registered`/`confirmed`/
   `joined`/`wrote` (`OverviewService.cs:138-144`) and the client supplies the wording via
   `FUNNEL_STAGE` (`AdminOverview.jsx:18-23`), the same rule as system messages and audit
   entries. `AdminOverview.jsx:115-120` builds each row as
   `{label: stage.key, color: 'text.disabled', ...stage, ...FUNNEL_STAGE[stage.key]}`: for
   an unrecognised key the last spread is `undefined` (a no-op), so the row keeps its raw
   key as the label rather than vanishing — a client one deploy behind a new stage shows
   something odd instead of a funnel that quietly loses a bar.
6. **Weekday letters are derived client-side** (`AdminOverview.jsx:32-37`), because the
   server does not know the reader's timezone.
7. **Every stat card links into the members table with the matching filter**
   (`AdminOverview.jsx:158`, `onNavigate('members')` on each card) — a number you cannot act
   on is decoration.

## Invented hints removed

Three literals survived from the design handoff into a screen whose numbers were otherwise
real: `"+3 in the last 30 days"`, `"2 expire within a week"`, and a funnel footnote reading
`"{data.pending} people have an open invitation. Two expire within seven days"` — the worst
of the three, because its first half (`data.pending`) was already real and lent the
invented second half its credibility. All three are now counted (`JoinedRecently`,
`ExpiringSoon`), with plurals and zero-cases handled explicitly
(`AdminOverview.jsx:70-138`). The general lesson, worth carrying past this note: a real
number sitting beside an invented one is more dangerous than a wholly fake panel, because
the fake panel is at least uniformly untrustworthy — nobody cross-checks a stat card.
