| 2026-08-21 | [Who gets written, and what everyone gets told](2026-08-21-profile-update-identity-and-broadcast.md) | fix | Issues #94 and **#99**, two genuinely different defects in the same six-line method, shipped together because fixing either alone leaves the other live. **#99 is account takeover**: `UpdateProfile` read `User.Identity.Name` into a local, never used it, and keyed the write on the caller-supplied `model.Id` — so any authenticated user could rewrite any other account's username and email. Reproduced live against two unrelated accounts before a line of fix was written (`HTTP 200`, victim's address replaced), and it is takeover rather than vandalism because password reset sends to the **stored** address: rewrite it, request a reset, receive the link — while the victim loses their own reset, their address no longer matching a row. The fix is small (take the id from the token, ignore the body's) and `GetProfile` immediately above always did it correctly — only this method disagreed; an unknown id now answers 401 like `GetProfile` rather than throwing a 500. **#94 is over-disclosure**: the broadcast to `Clients.All` was the *client-supplied* `ProfileViewModel` carrying `Email` and `Role`, so every connected client learnt any user's email on every profile save, and fields the server never persists were echoed back exactly as the caller wrote them. Now a purpose-built three-field projection built from the **persisted entity after `SaveChanges`**, with the avatar routed through `AvatarVisibility` so #89's retention marker is not undone — tested, because the marker leaves `AvatarFileName` populated and a raw read would resurrect a removed photo. **Re-running the attack against the fixed build exposed a third defect**: the request that no longer touches the victim renamed the *attacker's own* row into the victim's username, leaving two rows called `victim94` — `isUsernameUniq`/`isEmailUniq` are called only in register, never on update, and no unique index exists (**#100**). Generalisable: fixing an authorization hole can expose an integrity hole that was always behind it. 324/2/326 (was 318/2/320); live socket frame confirmed to carry no email and no role. |
| 2026-08-20 | [Removing an avatar, and why Undo forced a soft delete](2026-08-20-avatar-removal.md) | change | Issue #89, completing the avatar arc (#84 crop → #92 phone → #88 re-crop → #89 remove). #84 and #88 both shipped Remove **absent and pinned by a test**; those pins are now rewritten to assert its presence rather than deleted. **The handoff's "no confirm, but a working Undo that restores the photo AND its crop" is what rules out a delete**, because one fact closes the design: the server cannot re-derive a crop — cropping has been client-side since #84 — so destroying the derived object on the button press makes Undo either impossible or a forced re-upload, the exact failure Adjust crop exists to prevent.
