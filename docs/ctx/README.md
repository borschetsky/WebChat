| 2026-08-09 | [Avatars stopped being re-downloaded: one signed URL per file per window](2026-08-09-stable-avatar-urls.md) | change | Every render re-fetched every avatar, and **two independent things caused it — only one was known**. The redirect carried `Cache-Control: no-store` deliberately, but even without it nothing would have cached: SigV4 puts the signing instant in the URL and signs over it, so two requests a second apart returned different `X-Amz-Date` and different signatures. A different URL is a cache miss by definition. Proven against the running stack before changing anything. The AWS SDK cannot pin the signing instant (`GetPreSignedUrlRequest` exposes `Expires`, not the clock), so the URL is **memoised** for a window rather than made deterministic. Safe only because every upload writes a fresh `{Guid}.{ext}` — a filename's bytes never change, so replacing an avatar is a guaranteed miss rather than a stale hit; it would be wrong against stable per-user filenames. The subtle number is `CacheableFor = min(window, lifetime − window)`: a URL handed out at the *end* of the window has only the difference left, so bounding `max-age` by the window alone would cache a redirect to something already expired. `appsettings.json` had pinned a 15-minute lifetime that silently overrode the new 30 default — the guard behaved correctly, but both numbers are now written down together. Verified end to end through the rebuilt container: before, different URLs and `no-store`; after, `stable URL: YES`, `private, max-age=300`, `X-Amz-Expires=1800`, distinct per file. 72 tests, 0 warnings under `-warnaserror`. Supersedes part of the 2026-08-03 R2 note. |
