# Research notes

Answers to open questions that needed facts from outside this repository — providers,
protocols, pricing, standards, libraries. Newest first.

Written by the **`researcher`** agent (`.claude/agents/researcher.md`). Give it a question
and the constraints that matter; it does the searching and writes the note.

These are **not** the same as [`../ctx/`](../ctx/README.md). A ctx note records what was done
to this repository and why. A research note records what is true of the world outside it, on
the day it was checked — so unlike ctx notes, **these expire**. Prices, free-tier limits and
library versions all rot. Every note carries the date it was verified; treat anything old as
a starting point rather than a fact.

| 2026-08-12 | [Content-addressed avatars, and whether MD5 is the right hash](2026-08-12-avatar-content-addressing-and-hash-choice.md) | Should avatars be stored content-addressed (deduplicated by hash), which hash, and how does that change the fix for #20? | **No — keep GUID filenames and fix #20 with a best-effort delete-on-replace plus a one-off orphan sweep.** The dedup rate here is ~0 and it is measurable: the pipeline re-encodes, so a photo re-saved at a different source quality yields different stored bytes — and the output is **not stable across CPU SIMD width** (same source → 11,593 / 11,608 / 11,631 bytes under AVX2 / SSE / scalar), so dedup would silently stop working after an instance move. The strongest-sounding argument, `Cache-Control: immutable`, **does not pay out**: the browser caches against the rotating SigV4 query string, not the object name, so the lever is `UrlLifetimeMinutes` (R2 max 7 days) — config, not architecture — and GUID names already give the immutability #46 relies on. Against nothing gained, dedup takes on the refcount problem and turns #20 from "leaked 17 kB object" into "deleted someone else's avatar", which is irreversible (no record of who owns a shared object). On MD5 honestly: collisions in JPEG/PNG are **instant** (UniColl, corkami) but second-preimage is not broken (2^123.4, RFC 6151), an attacker must own both halves, and the re-encode destroys the structural slack collisions live in — so MD5 would be *safe here* and is still wrong, because measured on SHA-NI hardware **SHA-256 is 3.3× faster** (2,115 vs 645 MB/s at 17 kB) and needs no package. BLAKE3 (`Blake3` 3.0.2, BSD-2) **lost to BCL SHA-256**; xxHash (`System.IO.Hashing` 10.0.11, MIT, not in the shared framework) is disqualified as an identity — non-cryptographic with untrusted uploaders. `ETag` is an MD5 for these objects but arrives *after* the PUT, so it cannot name one. Also flagged: a content-derived filename breaks the documented "GUIDs are not enumerable" property of the anonymous `/images/{name}` endpoint, creating an existence oracle — fix would be an HMAC-keyed hash. |
| 2026-08-11 | [Avatar crop: library choice, and baked-in vs. stored crop](2026-08-11-avatar-crop-library.md) | Which client-side library should crop and reposition an avatar inside a circle, and should the crop be applied before upload or stored as metadata? | **`react-easy-crop` 6.2.3 (MIT, +7.2 kB gz measured), cropping client-side and uploading the Blob — no server change at all.** React 19 does *not* separate the field: all six candidates install against `react@19.2.8` with no ERESOLVE. The **interaction model** does. `react-image-crop` (ISC, 2.3 M dl/wk) drags a *selection box* and has **no zoom prop at all** — wrong model for a phone. `react-avatar-editor` 15.1.0 is the right model, smaller (+3.5 kB gz), zero deps, ships the canvas export, and dev-depends on our exact stack (react 19.2.4 / vite 8 / vitest 4) — but its **published build is single-touch**: pinch-zoom was merged as PR #434 on 2026-04-01, *eleven days after* the 15.1.0 release, and no release has followed. It also **throws in jsdom** (`getContext` returns null), so it needs a `setup.ts` stub; `react-easy-crop` guards `ResizeObserver` and renders clean under React 19.2.8 in jsdom 30 with nothing added — verified by running it. Cropper.js v2 is MIT with **no commercial tier** (the licensing worry does not apply), but has no v2 React wrapper (`react-cropper` is stale since 2023 and still on cropperjs 1.x) and no built-in circle. MUI ships nothing — confirmed. On architecture: **bake the crop in**, because #46's memoised presigned URL is safe *only* against fresh-Guid filenames, so re-rendering a crop into the same key serves the stale face from two caches at once. EXIF is already handled at both ends (`AutoOrient()` server-side; `image-orientation: from-image` is the CSS initial value) — though `drawImage`+EXIF is de-facto, not specified. Unverified: whether every browser's `toBlob` JPEG passes `WriteHelper`'s narrow `FFD8FFE0/E1` magic-byte gate. |
| 2026-08-10 | [Admin console: charting licences and client-error ingestion](2026-08-10-admin-console-charts-and-client-errors.md) | What does the admin console in the new design handoff cost us in dependencies and licences, and how should client-error ingestion be built? | **Hand-roll the charts (`d3-scale` + `d3-shape`, ISC, +10 kB gz); wire Sentry rather than building `/api/client-errors`.** `@mui/x-charts` 9.11.1 is MIT and its bar chart *and* sparkline are free — but **`FunnelChart` ships only in `@mui/x-charts-pro`**, commercial at **$299/yr/dev**, no free tier for personal projects. Once the funnel is hand-drawn anyway, a library is poor value: measured locally, `@mui/x-charts` costs **+100 kB gzip to draw one sparkline** (fixed engine cost — adding the bar chart only reaches +110), Recharts +97.5, own SVG **+10.0**. On errors, two repo facts make the spec's `fingerprint` uncomputable in production: `dist` ships **no sourcemaps** by deliberate decision, and Vite 8's minifier renames `AdminOverviewCard` to `t` (verified by building it), so `componentStack` is single letters that churn every deploy. Sentry's free plan (5 k errors/mo, 30-day retention, one user) does it for $0, and its issues API returns `count`, `userCount`, `culprit`, `lastSeen` and **`stats["14d"]` — the spec's sparkline, precomputed** — so build the screen against that API and skip ingestion, grouping and retention against a **512 MB** database. If you hand-roll anyway: pass literal boundary names rather than parsing `componentStack` (`captureOwnerStack` is `undefined` in production), never put hashed filenames in the fingerprint, and use `fetch(keepalive)` not `sendBeacon` — the latter cannot carry the `Authorization` header. **Audit log:** EF Core temporal tables are SQL-Server-only, and Audit.NET audits entity diffs rather than business events — own append-only table with a `BEFORE UPDATE OR DELETE` trigger. **Invitations:** "extend" should rotate *and* re-send, which collapses it into "resend". |
