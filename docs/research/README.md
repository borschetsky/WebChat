# Research notes

Answers to open questions that needed facts from outside this repository — providers,
protocols, pricing, standards, libraries. Newest first.

Written by the **`researcher`** agent (`.claude/agents/researcher.md`). Give it a question
and the constraints that matter; it does the searching and writes the note.

These are **not** the same as [`../ctx/`](../ctx/README.md). A ctx note records what was done
to this repository and why. A research note records what is true of the world outside it, on
the day it was checked — so unlike ctx notes, **these expire**. Prices, free-tier limits and
library versions all rot. Every note carries the date it was verified; treat anything old as
a starting point rather than a fact.

| 2026-08-15 | [Re-cropping an avatar, and whether to store the original](2026-08-15-avatar-recrop-and-original-storage.md) | Should the app let someone re-crop an existing avatar without re-picking the file, and does that mean storing an un-cropped original in R2? (#88) | **Keep the original client-side for the session — do not store one in R2.** `SettingsDrawer` already holds the picked `File` in `pickedPhoto` and discards it on confirm; keeping it plus the last `croppedAreaPixels` and reopening the dialog with `initialCroppedAreaPixels` (a real prop on the installed `react-easy-crop@6.2.3`, `index.d.ts:74`) is ~20 lines, no migration, no second R2 object, and **no interaction with #20 at all**. **Storage is not the reason to refuse** — measured, an original at 512 px JPEG q82 is **29.8 kB**, i.e. **$0.0045/month per 10,000 users** at $0.015/GB-month, well inside a free tier that holds 55,000–114,000 users in every variant. The real costs of storing originals are a migration through the `adapters.ts` drop-trap, a second object whose delete rule *differs* from the avatar's (replace deletes both; re-crop must **keep** the original — so #88 does not just double #20's leak, it changes what fixing it means), an anonymous `/images/{name}` endpoint now serving the part of the photo the user deliberately cropped out, and an "Adjust" button **invisible to every existing user** until their next upload. **Lifecycle rules are expressible but wrong**: prefix-scoped and age-based with **no last-access condition** (so "retire unused originals" cannot be written), and the Infrequent Access tier is a trap — *"The free tier only applies to Standard storage"*, so transitioning starts a bill plus a 30-day minimum and a retrieval fee to save a fraction of a cent. Re-deriving from the stored 256 px crop is **not viable** — the pixels needed are outside it. Crop rect: not needed server-side; if ever persisted, store **percentages**, not source pixels. **Incidental finding that dwarfs #88:** #84 exports PNG, and `AvatarImageProcessor`'s `keepAlpha` branch then stores PNG — measured **~87 kB vs ~9.4 kB for JPEG q82, 9.3×** — so raise a content-based (not format-based) alpha check on #84. The cache invariant everyone leads with was re-verified and holds, but decides nothing: every candidate design writes a fresh Guid anyway. |
| 2026-08-12 | [Vendoring .NET 10 docs: where they live, and what format serves an agent](2026-08-12-vendoring-dotnet-docs-format.md) | Where does authoritative, fetchable .NET 10 / C# documentation exist, and in what on-disk format should it be vendored into this repo? | **Fetch `learn.microsoft.com` with `Accept: text/markdown`, prune to one moniker, keep the prose verbatim, index it in a small table.** Learn serves plain markdown under content negotiation (`200 text/markdown; charset=utf-8`), and it is *not* the same document as the GitHub source: `aspnetcore/test/integration-tests.md` in `dotnet/AspNetCore.Docs` carries **36 `:::code source=` transclusions against 4 inline blocks** — the samples live in a separate repo and are simply *absent* — while Learn's variant has 137 inline blocks and zero `:::code`. That rules out cloning the docs repos the way `docs/vendor/react/` was cloned, and rules out GitHub entirely for `/dotnet/api/` pages, whose source is **ECMA XML** (`dotnet-api-docs`, `AspNetApiDocs`, `EntityFramework.ApiDocs`) with no markdown form anywhere else. The trap is that **`?view=` is ignored** by the markdown variant — `?view=aspnetcore-3.1` vs `aspnetcore-10.0` and `efcore-2.0` vs `efcore-10.0` both return **byte-identical** documents (267 383 and 21 514 bytes) — so what you get is the union of every version the page ever applied to, split by `::: moniker range="…"` markers whose ranges are helpfully **expanded to explicit version lists**. Pruning those to one version is the whole design: an unpruned page reads as authoritative .NET 10 prose while containing paragraphs last true in .NET Core 3.1. **No `llms.txt`** (404) and **no `.md` URL suffix** (404); the Learn MCP server (`learn.microsoft.com/api/mcp`, free, unauthenticated) is for live use and gives no commit to pin to. Learn's frontmatter carries `git_commit_id`, so provenance is exact and staleness-checking is re-fetch-and-compare-one-field. `applies-to-version` is the field that earns the header, because the URL's `?view=` is a lie. Also: `/dotnet/api/` **type** pages carry no moniker markers at all and stay version-ambiguous even after pruning — prefer the method page. Unverified: whether `Accept: text/markdown` is a supported feature or an implementation detail; no Microsoft documentation of it found. |
| 2026-08-12 | [Content-addressed avatars, and whether MD5 is the right hash](2026-08-12-avatar-content-addressing-and-hash-choice.md) | Should avatars be stored content-addressed (deduplicated by hash), which hash, and how does that change the fix for #20? | **No — keep GUID filenames and fix #20 with a best-effort delete-on-replace plus a one-off orphan sweep.** The dedup rate here is ~0 and it is measurable: the pipeline re-encodes, so a photo re-saved at a different source quality yields different stored bytes — and the output is **not stable across CPU SIMD width** (same source → 11,593 / 11,608 / 11,631 bytes under AVX2 / SSE / scalar), so dedup would silently stop working after an instance move. The strongest-sounding argument, `Cache-Control: immutable`, **does not pay out**: the browser caches against the rotating SigV4 query string, not the object name, so the lever is `UrlLifetimeMinutes` (R2 max 7 days) — config, not architecture — and GUID names already give the immutability #46 relies on. Against nothing gained, dedup takes on the refcount problem and turns #20 from "leaked 17 kB object" into "deleted someone else's avatar", which is irreversible (no record of who owns a shared object). On MD5 honestly: collisions in JPEG/PNG are **instant** (UniColl, corkami) but second-preimage is not broken (2^123.4, RFC 6151), an attacker must own both halves, and the re-encode destroys the structural slack collisions live in — so MD5 would be *safe here* and is still wrong, because measured on SHA-NI hardware **SHA-256 is 3.3× faster** (2,115 vs 645 MB/s at 17 kB) and needs no package. BLAKE3 (`Blake3` 3.0.2, BSD-2) **lost to BCL SHA-256**; xxHash (`System.IO.Hashing` 10.0.11, MIT, not in the shared framework) is disqualified as an identity — non-cryptographic with untrusted uploaders. `ETag` is an MD5 for these objects but arrives *after* the PUT, so it cannot name one. Also flagged: a content-derived filename breaks the documented "GUIDs are not enumerable" property of the anonymous `/images/{name}` endpoint, creating an existence oracle — fix would be an HMAC-keyed hash. |

| 2026-08-10 | [Admin console: charting licences and client-error ingestion](2026-08-10-admin-console-charts-and-client-errors.md) | What does the admin console in the new design handoff cost us in dependencies and licences, and how should client-error ingestion be built? | **Hand-roll the charts (`d3-scale` + `d3-shape`, ISC, +10 kB gz); wire Sentry rather than building `/api/client-errors`.** `@mui/x-charts` 9.11.1 is MIT and its bar chart *and* sparkline are free — but **`FunnelChart` ships only in `@mui/x-charts-pro`**, commercial at **$299/yr/dev**, no free tier for personal projects. Once the funnel is hand-drawn anyway, a library is poor value: measured locally, `@mui/x-charts` costs **+100 kB gzip to draw one sparkline** (fixed engine cost — adding the bar chart only reaches +110), Recharts +97.5, own SVG **+10.0**. On errors, two repo facts make the spec's `fingerprint` uncomputable in production: `dist` ships **no sourcemaps** by deliberate decision, and Vite 8's minifier renames `AdminOverviewCard` to `t` (verified by building it), so `componentStack` is single letters that churn every deploy. If you hand-roll anyway: pass literal boundary names rather than parsing `componentStack` (`captureOwnerStack` is `undefined` in production), never put hashed filenames in the fingerprint, and use `fetch(keepalive)` not `sendBeacon` — the latter cannot carry the `Authorization` header. **Audit log:** EF Core temporal tables are SQL-Server-only, and Audit.NET audits entity diffs rather than business events — own append-only table with a `BEFORE UPDATE OR DELETE` trigger. **Invitations:** "extend" should rotate *and* re-send, which collapses it into "resend". |
